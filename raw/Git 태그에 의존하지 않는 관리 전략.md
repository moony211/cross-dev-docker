단일 저장소(Monorepo)에서 여러 이미지의 버전을 개별적으로 관리할 때, Git 태그만으로는 충돌이나 혼선이 생기기 쉽다. 이를 해결하기 위해 Git 태그에 의존하지 않는 3가지 관리 전략을 제안한다.

---

## 1. 버전 명세서(Manifest File) 방식

저장소 루트에 `versions.json` 또는 `versions.yaml`과 같은 설정 파일을 두고, 각 이미지의 버전과 의존성을 명시하는 방법이다.

- **구조:**
  ```json
  {
    "cross-build": "1.2.0",
    "target-rootfs": "20240506",
    "qt-host": {
      "6.7.3": "v1.0",
      "6.8.3": "v1.1"
    }
  }
  ```
- **장점:** 이미지 간의 정합성을 한눈에 파악할 수 있으며, CI(GitHub Actions)에서 이 파일을 읽어 어떤 이미지를 빌드하고 어떤 태그를 붙일지 결정하기 매우 쉽다.
- **활용:** 특정 이미지의 버전 번호만 수정하고 커밋하면, GitHub Actions가 변경된 부분을 감지하여 해당 버전으로 도커 이미지를 빌드하고 Push한다.

---

## 2. 디렉토리별 `VERSION` 파일 관리

각 이미지 디렉토리 내부에 독립적인 `VERSION` 파일을 두는 방식이다.

- **구조:**
  ```text
  qt-host/6.7.3/VERSION  -> 내용: 1.0.0
  qt-host/6.8.3/VERSION  -> 내용: 1.1.0
  ```
- **동작 원리:**
  1. 개발자가 `qt-host/6.7.3/VERSION` 파일을 수정한다.
  2. GitHub Actions 트리거가 발생한다 (`on: push: paths: ['qt-host/6.7.3/VERSION']`).
  3. 스크립트가 해당 파일의 내용을 읽어 `docker build -t qt-host:6.7.3-$(cat VERSION) .` 명령을 수행한다.
- **장점:** 각 컴포넌트의 생명주기를 완전히 분리할 수 있다. 다른 이미지에 영향을 주지 않고 특정 Qt 버전만 업데이트하기에 최적이다.

---

## 3. Git Commit SHA 기반의 불변(Immutable) 태그

버전 번호를 직접 관리하는 번거로움을 피하고 싶을 때 사용하는 방식이다.

- **방식:** 도커 이미지 태그에 해당 시점의 Git Short SHA를 사용한다. (예: `qt-host:6.7.3-a1b2c3d`)
- **장점:** 어떤 소스 코드 시점에서 이미지가 생성되었는지 완벽하게 추적할 수 있다.
- **보완:** SHA만으로는 버전 구분이 어려우므로, 배포용 이미지는 `v1.0` 같은 별칭 태그를 추가로 부여하는 방식을 병행한다.

---

## 4. 추천하는 자동화 워크플로우 (GitHub Actions)

Git 태그 대신 **디렉토리별 변경 감지**와 **자동 레이블링**을 조합하는 것이 가장 효율적이다.

1.  **PR 기반 승인:** `cross-build/` 디렉토리 내의 파일이 수정되면 해당 이미지를 빌드하는 Worklfow가 실행되도록 설정한다.
2.  **환경 변수 활용:** `GITHUB_SHA`나 `GITHUB_RUN_NUMBER`를 빌드 번호로 사용하여 중복되지 않는 태그를 생성한다.
3.  **이미지 레이블링:** `Dockerfile` 내부에 `LABEL` 명령어를 사용하여 빌드 시간, 커밋 해시, 담당자 등의 메타데이터를 삽입한다.

---

## 요약 및 제언

- **가장 정석적인 방법:** 2번(**디렉토리별 `VERSION` 파일**) 방식이다. 파일 수정 자체가 "새 버전 출시"라는 명확한 의도를 나타내며, CI 구성이 매우 직관적이다.
- **관리 효율성:** Qt와 같이 버전이 나뉘는 경우, `VERSION` 파일 내부에 해당 Qt 버전과 매칭되는 빌드 순번(예: `6.7.3-rev1`)을 기록하여 관리하는 것이 추후 롤백이나 유지보수 측면에서 유리하다.
